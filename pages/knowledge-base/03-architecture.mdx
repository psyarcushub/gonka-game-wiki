# Архитектура системы

> Слайд 3 презентации. Четырёхслойный пирог системы.

## Главный принцип

Архитектура разделена на слои так, чтобы изменения в одном слое не ломали остальные. Самый верхний слой видит пользователь, самый нижний работает с «железом».

## Четыре слоя (сверху вниз)

```
┌──────────────────────────────────────────────────────┐
│  1. Telegram Mini-App                                │
│     Что видит пользователь                            │
├──────────────────────────────────────────────────────┤
│  2. Слой адаптеров сети                              │
│     Переводчики между ядром и конкретными AI-сетями  │
├──────────────────────────────────────────────────────┤
│  3. Плоскость управления (Control Plane)              │
│     Мозг системы — реестр, биллинг, мониторинг        │
├──────────────────────────────────────────────────────┤
│  4. Инфраструктурное ядро                            │
│     Управление железом — GPU, Docker, телеметрия      │
└──────────────────────────────────────────────────────┘
```

## Слой 1. Telegram Mini-App

Мини-приложение внутри Telegram, которое видит пользователь.

**Что делает:**
- Визуализация фермы (своих нод)
- Статус нод (запущена / упала / обновляется)
- Дашборд метрик (заработано сегодня / месяц / год)
- Управление перезапуском и масштабированием (кнопки «рестарт», «купить ещё мощности»)

**Зачем именно Telegram:**
- Массовая аудитория (миллиард пользователей)
- Низкий порог входа: не нужно скачивать отдельное приложение
- Удобная интеграция с криптокошельками (TON)
- Push-уведомления через бот

См. также: [Игровой слой](/knowledge-base/07-game-layer).

## Слой 2. Слой адаптеров сети

Прослойка между Control Plane и конкретными AI-сетями.

**Что делает:**
- Модульные плагины: один адаптер = одна сеть
- Внутри адаптера спрятана вся специфика: версии клиентов, формат метрик, особенности конфигурации
- Установка, обновления, парсинг метрик вознаграждений — всё внутри адаптера

**Зачем нужен:**

Чтобы Control Plane не знал ничего про конкретные сети. Он отдаёт общую команду — «разверни ноду на сети X» — а уже адаптер сети X переводит её в действия, понятные конкретной сети.

Если завтра появится новая сеть — добавляется новый адаптер, остальная система не меняется. Это и есть «модульность».

Подробнее: [Адаптеры](/knowledge-base/05-network-adapters).

## Слой 3. Плоскость управления (Control Plane)

«Штаб» всей системы. Один или несколько серверов, к которым подключены все ноды.

**Что делает:**
- **Реестр нод** — список всех зарегистрированных GPU-серверов с их характеристиками
- **Движок развёртывания** — запускает ноды по команде через адаптеры
- **Оркестрация обновлений** — рассылает новые версии клиентов нодам в правильное время
- **Агрегация мониторинга** — собирает телеметрию со всех нод в один поток
- **Биллинг** — считает, сколько заработала каждая нода, сколько списать с пользователя комиссии

Это центральный мозг. Если он упадёт — система парализована. Поэтому в Фазе 2 (см. [Roadmap](/knowledge-base/09-roadmap)) Control Plane получит «закалённую» версию с авто-восстановлением и защищённой аутентификацией.

## Слой 4. Инфраструктурное ядро

Самый низкий уровень — то, что работает прямо на GPU-серверах.

**Что делает:**
- **Управление GPU** — определение типа карты, объёма VRAM, версии драйверов
- **Оркестрация контейнеров Docker** — запуск нод как изолированных контейнеров
- **Жизненный цикл нод** — от установки агента до остановки
- **Телеметрия** — сбор метрик прямо с железа

На каждом GPU-сервере живёт «**легковесный агент**» — небольшая программа, которая принимает команды от Control Plane и выполняет их локально (запустить контейнер, остановить, переключить версию).

См. также: [Жизненный цикл ноды](/knowledge-base/04-node-lifecycle).

## Ключевой архитектурный принцип

**Цитата из презентации:**

> Трёхслойная архитектура обеспечивает независимость ядра оркестрации от конкретных сетевых протоколов, позволяя быстро интегрировать новые AI сети через модульные адаптеры.

(Примечание: в презентации сказано «трёхслойная», но фактически нарисовано 4 слоя — Telegram Mini-App, адаптеры, Control Plane, инфраструктурное ядро. Возможно, имеется в виду «без UI», то есть три слоя серверной части.)

**Главная идея:** ядро не должно знать ничего про конкретные сети. Иначе при появлении новой сети — придётся переписывать ядро. А с адаптерами — добавляешь плагин и всё.
